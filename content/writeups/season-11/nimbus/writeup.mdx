### Exploring the Job Submission Endpoint & SSRF Filtering

Exploring the job creation endpoint reveals that it accepts YAML files in two ways:
1. **By a valid GitHub repository URL**
2. **By uploading the raw YAML file directly**

Submitting a job reveals that direct code execution via PyYAML deserialization on the frontend is blocked (`safe_load` is enforced). However, the application informs us that jobs are queued in an AWS environment (region `us-east-1`) inside an SQS queue named `nimbus-jobs`, which a backend component (`nimbus/worker`) processes on a scheduled interval (`*/5 * * * *`).

The AWS metadata service IP (`169.254.169.254`) is the endpoint where Nimbus's internal AWS access keys would be stored. However, the internal network filter blocks standard requests with an error message:

> `Error: Security policy: this URL targets an internal resource and has been blocked.`

Additionally, the URL validator requires the string `.yaml` to be present in the query parameters or URL path.

### Bypassing SSRF Filters via Octal IP Encoding

The default AWS IAM metadata security credential endpoint is:
```text
/latest/meta-data/iam/security-credentials/
```

If we convert the IPv4 address `169.254.169.254` into **OCTAL** numbers, we can bypass the string and CIDR blacklist checks!

- `169` in octal = `0251`
- `254` in octal = `0376`

Thus, `169.254.169.254` becomes `0251.0376.0251.0376`!

We construct the SSRF payload with the `.yaml` extension requirement satisfied as a query argument:

```text
http://0251.0376.0251.0376/latest/meta-data/iam/security-credentials/?a=test.yaml
```

This bypasses the filter and returns the attached IAM role identity:

```text
nimbus-web-role
```

Now we query the specific role to extract its AWS credentials:


```python
"""Nimbus job worker. Polls SQS, parses messages with yaml.load (vulnerable)."""
import os, time, subprocess, boto3, yaml

ENDPOINT  = os.environ.get("AWS_ENDPOINT_URL", "http://aws.nimbus.htb")
QUEUE_URL = os.environ.get("QUEUE_URL", "http://aws.nimbus.htb/000000000000/nimbus-jobs")
REGION    = os.environ.get("AWS_DEFAULT_REGION", "us-east-1")
POLL_SECS = 5

print(f"[worker] starting; endpoint={ENDPOINT} queue={QUEUE_URL}", flush=True)
sqs = boto3.client("sqs", endpoint_url=ENDPOINT, region_name=REGION)

def handle_message(body):
    print(f"[worker] received message ({len(body)} bytes)", flush=True)
    job = yaml.load(body, Loader=yaml.Loader)  # vulnerable
    if not isinstance(job, dict):
        print("[worker] message did not parse to a dict, skipping", flush=True)
        return
    name = job.get("name", "<unnamed>")
    script = job.get("script", "")
    print(f"[worker] running job '{name}'", flush=True)
    if script:
        result = subprocess.run(["python3", "-c", script],
            capture_output=True, text=True, timeout=30)
        print(f"[worker] stdout: {result.stdout}", flush=True)
        if result.stderr: print(f"[worker] stderr: {result.stderr}", flush=True)

def main():
    while True:
        try:
            resp = sqs.receive_message(QueueUrl=QUEUE_URL,
                MaxNumberOfMessages=1, WaitTimeSeconds=POLL_SECS)
            for m in resp.get("Messages", []):
                try: handle_message(m["Body"])
                except Exception as e: print(f"[worker] error: {e}", flush=True)
                finally:
                    sqs.delete_message(QueueUrl=QUEUE_URL, ReceiptHandle=m["ReceiptHandle"])
        except Exception as e:
            print(f"[worker] poll error: {e}", flush=True)
            time.sleep(POLL_SECS)

if __name__ == "__main__":
    main()
```

#### Key Technical Takeaways:
1. **Unrestricted PyYAML Constructor:** The developer used `yaml.Loader` instead of `yaml.SafeLoader`. Even though the web frontend parsed inputs with `safe_load`, this background worker reads raw strings from SQS and deserializes them without restrictions.
2. **Direct Subprocess Command Execution:** The worker extracts the raw string under the `script` key and passes it straight to `subprocess.run(["python3", "-c", script])`.
3. **Queue Dequeue Cycle:** Messages are read, handled, and deleted via their `ReceiptHandle` regardless of whether execution succeeds or crashes.

### Understanding AWS CodeBuild Architecture

Next, we discover that our credentials have IAM access to the **AWS CodeBuild** service on `http://floci:4566`.

> **What is AWS CodeBuild?**
> AWS CodeBuild is a fully managed continuous integration (CI) service in the cloud. It automates the process of compiling source code, running tests, and producing ready-to-deploy software packages.

#### How CodeBuild Works Under the Hood

```
[Trigger Build] ➔ [Spins up temporary Docker Container] ➔ [Executes Buildspec Commands]
```

1. **The Container:** CodeBuild spins up a temporary, isolated Docker container using an operating system image specified by the developer (e.g., Ubuntu with Python pre-installed).
2. **The Buildspec:** Inside this container, CodeBuild looks for a `buildspec.yml` recipe card in YAML format that lists operating system commands to execute (e.g., `npm install`, `python3 test.py`).
3. **The Cleanup:** Once commands complete, CodeBuild saves output packages to S3 and destroys the temporary container.

### Container Breakout: /proc/sys/kernel/modprobe & OverlayFS Upperdir

After deeper enumeration of the privileged container environment, I observed that `/proc/sys/kernel/modprobe` is writable!

#### What is `/proc/sys/kernel/modprobe`?

The `/proc` filesystem is a virtual interface to kernel data structures:
- **Purpose:** `/proc/sys/kernel/modprobe` contains the binary path invoked by the kernel to load modules (defaults to `/sbin/modprobe`).
- **Mechanism:** When the Linux kernel encounters an unknown binary signature or unhandled device request, it triggers `call_usermodehelper` using the path stored in this file.

```
       Creating the crafted payload!
                     |
       Overwriting the modprobe path
                     |
       Trigger with unknown file signature (\xff\xff\xff\xff)
                     |
       Kernel executes the path as ROOT on HOST!
```

#### The Container Escape Challenge: Host vs. Container Paths

Can we simply write `/tmp/payload.sh` into `/proc/sys/kernel/modprobe`?

**No!** The host kernel executes the usermode helper outside the container filesystem. It has no visibility into container-namespaced paths like `/tmp/payload.sh`.

#### Finding the Physical Disk Path with OverlayFS `upperdir`

Containers use OverlayFS to merge image layers. New and modified files reside in the `upperdir` mount directory on the host:

```bash
upper=$(awk '/overlay/{match($0,/upperdir=([^,]+)/,a);if(a[1])print a[1]}' /proc/mounts | head -1)
```

The physical host-side path to `/tmp/payload.sh` is:
```text
$upper/tmp/payload.sh
```

## Step 5 - Mitigations & Defensive Hardening

To remediate the vulnerabilities identified across the Nimbus environment, administrators and cloud architects should apply defense-in-depth hardening across application, CI/CD, and host kernel layers:

### 1. AWS Instance Metadata Service (IMDSv2) Enforcement & SSRF Defense
- **Enforce IMDSv2 Globally:** Mandate IMDSv2 (`HttpTokens=required`) across all EC2 instances and container hosts. This requires attackers to issue a `PUT` request with `X-aws-ec2-metadata-token-ttl-seconds` to acquire a session token, defeating blind SSRF.
- **Normalize and Canonicalize Network Inputs:** When validating user-supplied URLs or IP addresses, resolve all representations (including octal `0251.0376.0251.0376`, hex, or integer IP formats) before checking against blacklists.
- **Network-Level Metadata Blocking:** Implement local firewall rules or iptables chains prohibiting non-root container processes from routing to the link-local metadata address (`169.254.169.254/32`).

### 2. Secure Serialization & PyYAML SafeLoader Enforcement
- **Eliminate Unrestricted Constructors:** Replace all occurrences of `yaml.load(body, Loader=yaml.Loader)` with `yaml.safe_load(body)` or `yaml.load(body, Loader=yaml.SafeLoader)` across all background workers, microservices, and queue consumers.
- **Input Schema Validation:** Strictly validate and sanitize message schemas before executing any subprocess or script evaluation. Never pass unvetted strings directly to `subprocess.run(["python3", "-c", ...])`.

### 3. CI/CD Pipeline Least Privilege & Container Sandbox Isolation
- **Disable Privileged Mode:** Disallow `privilegedMode: true` in AWS CodeBuild and local runner profiles. Running build tasks in privileged containers drops Docker boundary isolation and confers full `CAP_SYS_ADMIN` privileges.
- **Enforce IAM Role Scoping:** Restrict IAM permissions attached to CI/CD service roles (`arn:aws:iam::...:role/codebuild-role`). Worker daemons should only possess permissions necessary for their immediate task, preventing unauthorized build execution.
- **Ephemeral Non-Root Runners:** Execute all CI/CD build scripts as non-root users inside unprivileged ephemeral containers with drop-capabilities enabled (`--cap-drop=ALL`).

### 4. Linux Kernel Parameter Hardening & /proc/sys Protection
- **Mount /proc/sys as Read-Only:** Ensure that `/proc/sys` is mounted strictly read-only inside all container environments. Non-privileged container runtimes enforce this by default; never override it with custom volume mounts.
- **Kernel User Mode Helper Auditing:** Deploy Linux kernel auditing rules (`auditd`) to monitor write attempts to `/proc/sys/kernel/modprobe` and alert on unauthorized binary execution via `call_usermodehelper`.
- **LSM & AppArmor Profiles:** Deploy enforcing AppArmor or SELinux profiles that prevent container processes from altering kernel parameters or accessing host filesystem paths via OverlayFS layers.
